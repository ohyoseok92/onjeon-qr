# 백업 분리 보관과 복구 승인

`scripts/backup_custody.py`는 최신 암호화 백업을 확인한 뒤 백업 파일과 복구 키를 서로 다른 매체에 복사한다. 원본 프로필·백업·설정을 보존하며 기존 출력 파일을 덮어쓰지 않는다. 복사 성공만으로 서비스를 재개하지 않는다. 백업 이후의 폐기와 토큰 교체는 별도 확인이 필요하다.

## 분리 보관 기준

암호화 백업은 원본·키 보관처와 독립된 매체에 둔다. Windows에서는 드라이브 문자 대신 물리 디스크의 `UniqueId`를 비교한다. 같은 디스크의 다른 파티션이나 폴더는 독립된 매체로 인정하지 않는다. UNC 경로는 서버 주소를 확인하며 같은 서버의 공유 두 곳, DNS 별칭, 현재 PC를 가리키는 공유도 독립 대상으로 인정하지 않는다. 물리 디스크를 확인할 수 없는 가상 디스크와 POSIX 경로는 완료로 처리하지 않는다.

기본 모드는 원본과 키를 같은 PC에 보관하고 암호화 백업을 원격 서버에 보관하는 구성을 허용한다. 결과에 원본·키의 같은 매체 사용을 표시한다. 원본·키까지 분리하려면 `--require-three-media`를 추가한다. 다른 물리 디스크로 복사해도 오프사이트 보관을 자동 증명하지는 않는다. UNC 원격 호스트를 실제 확인했을 때만 `archive_off_host_verified=true`를 기록한다. 원본과 키가 함께 있으면 같은 PC의 침해·손실로 둘 다 잃을 수 있으므로 별도의 키 복구 수단과 접근 통제를 운영자가 확인해야 한다.

원격 호스트 확인은 물리적인 오프사이트 위치나 서로 다른 사업자를 증명하지 않는다. 다중 NIC·클러스터·별도 DNS 별칭을 쓰는 서버는 운영자가 승인한 인프라 기록으로도 확인해야 한다. 저장소 주소·장애 영역·위치를 승인한 기록 없이 `archive_off_host_verified=true`를 오프사이트 보관 완료로 해석하지 않는다.

대상 부모 폴더는 운영자가 미리 만들어 현재 사용자와 SYSTEM만 접근할 수 있도록 보호해야 한다. 도구는 경로의 심볼릭 링크·Windows reparse point를 거부하고 파일별 권한을 검사한다. 네트워크 저장소가 이런 권한을 보장하지 않으면 복사는 실패한다. 이 경우 해당 저장소용 승인·암호화·접근 통제를 갖춘 별도 어댑터가 필요하다. 출력이 부분적으로 남아도 성공으로 기록하지 않으며 해당 산출물은 복구에 사용하지 않는다.

UNC 대상은 해당 서버·공유의 실제 `Get-SmbConnection` 결과에서 SMB 전송 암호화가 켜졌는지도 확인한다. 연결 관찰이 없거나 암호화가 꺼져 있으면 비밀 복구 자료를 보내기 전에 거부한다. SMB 서명만 켠 구성은 전송 암호화를 충족하지 않는다. 개인 클라우드 서비스에 파일을 올리는 API는 이 도구에 포함하지 않았다.

## 내보내기

다음 경로는 운영자가 지정할 실제 대상 경로로 바꾼다. 명령행에 암호나 키 내용은 넣지 않는다.

```powershell
.venv/Scripts/python.exe scripts/backup_custody.py export "<최신 AES-GCM 백업>" --profile "<백업을 만든 보호 프로필>" --archive-parent "<독립 백업 매체의 보호 폴더>" --custody-parent "<독립 키 매체의 보호 폴더>"
```

두 대상에 같은 이름의 새 하위 폴더를 만든다. 백업 대상에는 `state.onbackup`만 저장한다. 키 대상에는 `application/production.env`, 백업 AES 키, 최신 HMAC 인증 체크포인트, 릴리스 암호화 개인키·암호·공개키, 비공개 `recovery-record.json`을 저장한다. 체크포인트는 SQLite 트랜잭션 안에서 일관된 스냅숏으로 복사한다. 출처별 최신 체크포인트와 백업 메타데이터가 일치하지 않으면 내보내지 않는다.

복사 뒤 모든 바이트와 권한을 확인하고 대상 매체가 바뀌지 않았는지 다시 검사한다. 결과에는 백업 ID·세대·암호화 파일 SHA256·검사 결과만 담는다. 개인키, 암호, 환경 비밀, 토큰은 출력하지 않는다. 각 백업 주기마다 이 작업을 반복하고 접근 로그·매체 회수·보존기간·키 교체를 운영 기록에 남긴다. 같은 PC 임시 폴더에서의 합성 시험은 실제 분리 보관 완료로 해석하지 않는다.

## 복구 중 최신 보안 상태 확인

1. 복구 서버의 공개 발급·검증·관리 진입점을 격리한다. 기존 서비스의 변경을 정지하고, 권한이 있는 운영자가 복구 전환 시점까지의 기관·키·QR 폐기와 토큰 교체를 포함한 원본을 SQLite backup API로 별도 스냅숏으로 만든다. 실행 중 DB 본체만 복사하지 않는다.
2. 스냅숏을 비공개로 보관하고 그 SHA256 및 설치 식별자, 마지막 변경 시각, 변경 정지·전환 승인 기록을 백업 저장소와 독립된 신뢰 채널에 기록한다. DB 옆에 저장된 해시를 그대로 신뢰하면 안 된다. 이후 변경이 발생하면 이전 확인을 무효화하고 새 기록을 만든다.
3. 독립 키 매체에서 새 비공개 복구 프로필을 구성한다. `secure_profile.py restore`가 최신 체크포인트를 확인하게 하고 기존 DB·키·HMAC를 덮어쓰지 않는다. 체크포인트 유실 시에는 독립 기록의 최신 백업 ID만 `--expected-backup-id`로 사용한다. 새 설치 승인이나 `--allow-rollback`으로 기록 유실을 숨기지 않는다.
4. 백업 뒤 승인된 변경을 격리된 복구 서버에 재적용한다. 승인 기록 없이 폐기가 없었다고 추정하지 않는다. 관리자 비밀은 새 CSPRNG 값으로 교체한다. 발급키·HMAC·기관 토큰의 복구 권한도 확인한다.
5. 아래 검사를 실행한다. 기관 상태·공식 도메인·토큰 해시·키 공개키와 활성/폐기 상태·발급 QR의 전체 보안 메타데이터가 정확히 일치해야 한다. 다른 설치, 다른 해시, 손상 DB, 병합하지 않은 WAL, 검사 도중 바뀐 원본은 거부한다. 민감한 행 내용은 출력하지 않는다.

```powershell
.venv/Scripts/python.exe scripts/backup_custody.py verify-recovery "<복구 DB>" --authoritative "<신뢰 채널로 확인한 정지 시점 원본 스냅숏>" --expected-security-sha256 "<독립 기록의 64자리 SHA256>"
```

6. QR·키 폐기, 비활성 기관, 교체 전 토큰 거부와 새 토큰 발급을 실제 API에서 확인한다. 새 관리자 비밀, 운영 TLS·CRL, 권한, 요청 제한, 백업 재개를 확인한 뒤 승인 담당자가 전환한다. 검사 결과는 `service_recovery_authorized=false`를 유지한다. 도구가 운영자의 최신성·전환 승인을 대신하지 않는다.

원본이나 신뢰 기록을 잃어 최신 상태를 확인할 수 없으면 서비스 격리를 유지한다. 특히 기존 QR 검증을 공개하면 폐기된 QR이 되살아날 수 있다. 이때는 기존 기관·키·QR을 일괄 비활성/폐기하는 승인된 절차와 새 토큰·새 키·재발급 계획을 먼저 마련해야 한다. 새로운 신뢰 상태가 확정되기 전 서비스를 열지 않는다.

## 검증 범위

`tests/test_backup_custody.py`는 합성 DB와 무작위 키만 사용한다. 실제 private ACL, 암호화 백업과 복구 파일의 동일성, 원본 보존, 출력 경로 충돌 방지, 최신 세대·변조 거부, 외부 보안 상태 해시 불일치, 복구 뒤 폐기 불일치, WAL 잔존, 동일 디스크·원격 서버 중복 거부를 확인한다. 별도 물리 매체와 원격 서버 판별은 시험용 관찰값으로 주입하므로 시험 통과만으로 실제 외부 보관을 완료했다고 주장하지 않는다.

실제 완료 증거에는 승인된 대상, 원본·키와 암호화 백업의 독립성 및 오프사이트 검사, 암호화 복사 검증, 독립 복구 ID 보관, 최신 보안 상태와 전환 승인, 정기 복구 결과가 필요하다. 현재 대상과 승인 기록이 지정되지 않은 부분은 운영 입력 대기 상태다.

### 실행 결과 (2026-10-11)

Windows의 최신 전체 시험은 **12개 통과·1개 생략, 175.09초**로 끝났다. 생략한 항목은 권한이 필요한 Windows 디렉터리 심볼릭 링크 생성 시험이며 POSIX 시험에서 실행한다. 실제 NTFS ACL로 새 보호 폴더와 복구 자료의 권한을 검사했다. 현재 보호 프로필의 물리 디스크 조회도 성공했으며 식별자 값은 보고서에 남기지 않았다. `bandit scripts/backup_custody.py -q`는 검출 없이 종료했고 CLI 도움말과 문법 검사도 통과했다. 외부 대상과 오프사이트 보관 완료는 아직 확인하지 않았다.
