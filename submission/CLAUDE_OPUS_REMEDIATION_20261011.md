# Claude Opus 지적 수정·검증 결과

확인일: 2026-10-11. 원래 지적 5건을 수정했고 Claude Opus High의 후속 정적 검토에서 5건 모두 해결 판정을 받았다. 추가 검토에서 나온 백업 신뢰 체인의 분기와 health 비용도 보완했다. 마지막에 남은 첫 백업 자동 승인 Low(R1)는 명시적 승인 옵션으로 추가 수정하고 회귀시험으로 확인했다. R1의 최종 코드 변경은 아래 마지막 Claude 검토 이후에 적용했으므로 독립 재검토 통과로 표현하지 않는다.

## 수정 내용

| 원래 지적 | 반영한 수정 |
|---|---|
| M1 Medium: 공개 요청이 관리자 용량 소진 | 고정6그룹 각각1만행 상한, 지난 분 정리·현재 한도 보존. 인증 실패는 별도 그룹. 기존 CHECK 마이그레이션에서도 현재 카운터 보존. 역할별8개 인증 분류 동시성 상한과 예외 후 슬롯 반환 |
| L1 Low: fec0 IPv6 필터 누락 | site-local IPv6를 명시 차단하고 혼합 DNS 응답도 연결 전에 거부 |
| L2 Low: 백업 시점·롤백 식별 부족 | AES-GCM 인증 생성시각/설치ID/세대/감사ID/DB해시. DB 안의 고정 설치ID로 경로가 바뀌어도 동일 체인 유지. 스냅숏·세대 할당 직렬화, 별도 HMAC 체크포인트와 기본 복구 대조. 이전·v1·경로기반구형v2 기본 거부 |
| L3 Low: 평면 키 경로 충돌 | 운영 모드는 기관ID/키버전.pem 중첩 경로만 사용. local 데모 호환은 유지 |
| L4 Low: CRL 만료 시 전체 시작 실패 | 정상형식 CRL의 시간문제는 URL 분석만 차단. 서명 QR·관리 기능 유지, health의 고정 degraded 상태 표시. 누락/손상/CA혼입/역전/키로그 설정은 시작 거부. health는5초 상태 캐시, 실제 TLS 검사는 매요청 strict |

## 후속 발견과 마지막 보완

- N1 Medium: staging 경로마다 백업 세대가 갈라지던 문제를 DB 설치ID로 해결했다. 같은 DB를 다른 경로로 옮겨도 오래된 백업 기본 복구와 낮은 감사ID의 새 세대 재포장을 거부한다.
- N2 Low: 인증 평가 뒤의 실패 lane은 토큰 평가 자체의 분당 제한이 아니다. 역할별 동시성 상한을 추가하고, 높은 엔트로피 토큰·앞단 부하 통제·경보가 필요한 설계 조건을 명시했다. 정상·실패 기관 요청도 같은 역할 슬롯을 공유한다. Claude는256bit 토큰 모델에서 악용 가능한 결함 대신 문서화된 설계 선택으로 판정했다.
- N3 Low: 공개 health가 매번 CRL을 파싱하던 비용은 앱별 잠금/5초 캐시로 해결했다. 실제 URL 분석의 허용 판단에는 캐시를 쓰지 않는다.
- R1 Low: 처음 보는 설치의 첫 백업은 이제 기본 거부한다. 독립 신뢰 기준을 확인한 운영자만 `--new-installation` 또는 `approve_new_installation=True`로 승인한다. ID를 잃은 구형 DB를 초기화해 새 ID가 생겨도 조용히 새 체인으로 등록되지 않는다. 결과에 승인 사실을 기록한다. 마지막 Claude 원문에 남은 Low를 이 후속 수정으로 구분한다.
- 재연결: 체크포인트를 잃었을 때 독립 기록의 `--expected-backup-id`로만 다시 연결하고 결과에 기록한다. 존재하는 최신 체크포인트를 외부의 오래된 ID로 우회할 수 없다. 알려진 체크포인트 재확인·INSERT를 파일 쓰기 전에 수행해 재연결 경합을 안전하게 거부한다.

## 실제 실행 증거

- 최종 제품 이미지: `sha256:1b5c6bed0b940e956d1debb854a9e2d14ec5e848a3475de9da4ee1ad709ef910`.
- Linux 전체 회귀: **176 passed, 1 skipped, 1 warning — 25.43초**. 상세는 `TEST_REPORT.md`를 따른다. POSIX 권한 시험 포함, npm 설치가 없는 공급망 통합 시험1개 생략, Starlette의 기존 경고1개.
- Windows 새 결함 회귀12개 통과(135.93초), 수정된 기존4모음120개 통과/1생략(91.79초). R1 최종 추가 시험은 Linux에서 별도 확인했다.
- Docker 실제 TLS1.3·발급→trusted→폐기→blocked, 재시작 후 폐기/제한 유지, UID10001·0600/0700·CapEff0·NoNewPrivs1·read-only rootfs/비밀bind, 실행 소스 hash 일치.
- 실제 정지 시점 DB·기관별 암호화 키·HMAC의 암호화 백업/복구와 production API/관리자 인증 성공. 최신 상세 수치는 `DOCKER_BACKUP_CHECK.json`을 따른다.
- 최종 이미지 패키지 재검사: 당일 동일 공개 DB, OS38/Python21, 모든 등급 검출0. `DOCKER_IMAGE_SCAN.json` 마지막 scan이 최종 이미지와 일치한다.

검증 중 기존 한도 시험의61번째 요청이200이 되는 실패1회를 관찰했다. 이 시험은 UTC 분 경계를 제어하지 않았다. 고정 시계를 시험에만 주입해 실제 창 전환을 한도 초과로 혼동하지 않도록 수정했다. 제품의 한도는 바꾸지 않았다. 실패 원문은 비공개 로컬 로그에 보존하며 임시 토큰을 제출 보고서에 복사하지 않았다.

## Claude 실행과 범위

실제 Claude Code2.1.287에서 `--model opus --effort high`를 사용했다. 두 후속 실행의 응답 모델은 모두 `claude-opus-5-5`다. 첫 후속 검토280.44초/Read9경로, 마지막 검토206.94초/Read7경로와 관련 Grep으로 수정 범위를 확인했다. 각 격리 사본은 변경되지 않았다. 비밀키·실제 DB·백업 평문은 제공하지 않았고 Read/Glob/Grep만 허용했다. Claude가 테스트나 컨테이너를 직접 실행한 결과는 아니다.

마지막 독립 검토 이후 제품 API/저장소/분석기 소스는 동일하다. R1 첫 백업 승인과 복구 재연결 쓰기 순서는 `secure_profile.py`에서 이후 보완했다. 관련 테스트와 실제 복구 도구도 이 명시적 승인 계약에 맞췄다. 아래 원문은 발견과 판정을 보존한 기록이며 현재 수정 상태는 위 표·실행 증거를 따른다.

## 남는 운영 조건

공개 TLS/별도 신뢰 매체(S05), 운영 CRL 확보·갱신·역행 방지(S11), 발행자 신원·외부 지문 신뢰/CI runner(S15)는 실제 배포 환경에서 확인해야 한다. 최신 백업도 이후 폐기를 알 수 없으므로 백업 생성시각·감사ID 이후의 QR/키 폐기·기관 비활성·토큰 교체를 재적용하고 승인한 뒤 재개한다. 같은 설치ID의 독립 복제본은 감사 MAX(id)만으로 전체 계보가 증명되지 않아 승인된 운영 원본만 백업해야 한다. 키/체크포인트까지 되돌릴 수 있는 공격자를 로컬 기록만으로 차단한다고 주장하지 않는다.

Alpine 미수정 취약점과 휠 번들 네이티브 라이브러리까지 검출0이 보장하는 것은 아니다. 기존 참고 가이드 기록과49항목 점검표의36구현/10비적용/3운영조건 집계는 그대로 구분한다.

## 1. 원 지적별 판정

### M1 — 공유 rate-counter 용량 / 잘못된 인증으로 인한 lane 오염 → **해결 (잔여 사항 있음)**

- **그룹별 고정 용량:** 6개 그룹이 각자 10,000행 상한을 가집니다(`storage.py:77-78`). 그룹별로 `COUNT(*)`를 세고(`storage.py:132-136`), 용량이 차면 기존 카운터를 지우지 않고 거부합니다. 따라서 퇴출(eviction)을 이용한 쿼터 우회는 확인되지 않았습니다.
- **현재 분 기준 정리:** `_prune_rate_counters`는 현재 분보다 오래된 행만 지웁니다(`storage.py:108-110`). 지난 분의 행이 이번 분의 용량을 차지하지 않습니다.
- **마이그레이션:** 시작 시 `BEGIN IMMEDIATE` 트랜잭션 안에서 새 테이블을 만들고, 행을 복사하고, 기존 테이블을 DROP한 뒤 이름을 바꿉니다(`storage.py:200-211`, `230-236`). 인덱스는 이후 `storage.py:248`에서 다시 만들어집니다. 현재 창의 카운트는 보존됩니다(`test_storage.py:148-171`). 예전 스키마가 예상과 다르면 INSERT…SELECT가 실패해 시작이 막히므로(fail-closed), 데이터가 조용히 사라지는 경로는 보이지 않습니다.
- **인증 사전 분류:** 미들웨어가 먼저 자격 증명을 확인하고, 실패하면 `group += "_auth"`로 별도 lane을 씁니다(`api.py:286-302`). 실제 권한 판단은 각 엔드포인트가 쓰기 트랜잭션 안에서 다시 합니다(`api.py:547`, `603`, `623`, 그리고 `dependencies=[Depends(require_admin)]`). 미들웨어의 사전 분류는 어느 lane을 쓸지만 정하고 권한을 주지 않습니다. 사전 확인과 엔드포인트 사이에 토큰이 교체되면 엔드포인트에서 403이 나므로, 이 경쟁 조건으로 우회되지는 않습니다.
- **잔여 사항:**
  - `issuer` lane의 키는 주소뿐이고 기관 ID를 포함하지 않습니다(`api.py:303-314`). NAT나 리버스 프록시 뒤에서는, 정상 토큰을 가진 한 기관이 다른 기관의 분당 30회 쿼터를 소진시킬 수 있습니다. 이번 변경 이전부터 있던 구조입니다.
  - lane 분리 때문에 새로 생긴 부작용은 아래 N2에 정리했습니다.

### L1 — `fec0::/10` SSRF → **해결**

- `_is_public_address`에 `address.is_site_local` 조건이 추가되었습니다(`analyzer.py:138-142`).
- 이 함수는 모든 홉에서 `_resolve_public`을 통해 호출되며, 해석된 주소 중 하나라도 공개 주소가 아니면 거부합니다(`analyzer.py:163-164`).
- 혼합 DNS 응답 테스트도 있습니다(`test_analyzer.py:253-255`).

### L2 — 백업 메타데이터 인증과 외부 HMAC 체크포인트 → **부분 해결**

**해결된 부분:**
- **메타데이터 인증:** 메타데이터가 AES-GCM 평문 안에 들어 있어 인증됩니다(`secure_profile.py:317-323`). 복원 시 `database_sha256`, 타입, UTC 여부를 검증합니다(`261-273`).
- **체크포인트 무결성:** HMAC과 `source_id` 바인딩을 확인합니다(`251-258`).
- **기본 거부 경로:** 체크포인트가 없거나 다르면 거부합니다(`389-390`). v1 백업은 명시 승인이 필요합니다(`350-351`). 체크포인트 파일이 없으면 외부에서 받은 백업 ID나 롤백 승인이 필요합니다(`393-394`).
- **쓰기 시점:** 체크포인트 검증이 끝난 뒤에만 복원 결과를 씁니다(`391`, `395`).

**부분 판정인 이유:** `source_id`가 원본 파일 경로에 묶여 있어서, 실제 운영 절차에서 롤백 거부가 무력화될 수 있습니다(아래 N1).

### L3 — 운영 환경 legacy 키 경로 충돌 → **해결**

- `_key_path(..., allow_legacy=not production)`이 키를 로드하는 세 곳 모두에 적용되었습니다(`api.py:445`, `490`, `556`). 운영 환경에서는 항상 중첩 경로만 씁니다(`api.py:197-201`).
- 충돌 사례(`aa-b/c` 대 `aa/b-c`)와 운영 거부를 다루는 테스트가 있습니다(`test_api.py:784-859`).
- 개발 모드에서는 여전히 평면 경로로 대체되지만, 등록된 공개키와 일치해야 사용되므로(`api.py:448`, `491`, `562`) 다른 기관 키로 서명되지 않습니다.

### L4 — 만료된 CRL 때문에 앱 전체가 시작하지 못함 → **해결**

- 잘 구성된 CRL이 만료되었거나 아직 유효하지 않은 경우에만 `reason`이 바뀌고, 모든 블록을 끝까지 검증합니다(`analyzer.py:86-96`). 형식 오류, CRL이 아닌 블록, 파일 교체 감지는 계속 예외를 냅니다(`83-84`, `100-105`).
- 요청 시점에는 `allow_stale_crl=False` 때문에 예외가 납니다(`106-107`). `_head` 호출이 try 안에 있어 `tls_invalid`/blocked로 처리됩니다(`analyzer.py:277-283`). fail-open 경로는 확인되지 않았습니다.
- 시작 시에는 로그만 남기고 계속 진행합니다(`api.py:227-230`). health는 고정된 사유 문자열만 반환합니다(`api.py:403-411`).
- 다만 health 경로에 새 비용 문제가 있습니다(N3).

## 2. 새로 발견한 조치 대상

### N1 — [Medium] 경로 기반 `source_id` 때문에 체크포인트 체인이 분기되어 롤백 거부가 무력화됨

- **코드:**
  - `source_id = HMAC(key, str(source.resolve()))` (`secure_profile.py:312`)
  - 체인마다 따로 `latest == metadata`를 비교 (`388-389`)
  - 감사 단조성 검사도 같은 체인 안에서만 동작 (`314-316`)
- **전제 조건:** 같은 논리 DB를 서로 다른 경로에서 백업한 경우입니다. 예를 들어 실행마다 다른 staging 경로를 쓰거나, 데이터 디렉터리를 옮기거나, 컨테이너 경로와 호스트 경로를 섞어 쓰거나, Windows에서 같은 경로를 다른 표기로 쓰는 경우입니다.
  - 제품의 Docker 백업 절차가 바로 이런 방식입니다. `staging-<timestamp>-<random>/data/onjeon.sqlite3`를 백업하므로(`check_encrypted_docker_backup.py:51`, `65`, `68`) 실행할 때마다 새 체인의 1세대가 됩니다.
- **영향:**
  - 각 체인의 마지막 백업이 영구히 "최신"으로 남습니다. 그래서 키 폐기, 기관 비활성화, QR 폐기 이전의 오래된 백업도 `allow_rollback` 없이 기본 경로로 복원되고, `rollback_explicitly_allowed: false`가 표시됩니다.
  - 백업 저장소를 조작할 수 있는 공격자나 운영 실수로 오래된 파일이 선택되어도 경고가 나오지 않습니다.
  - 같은 이유로 감사 ID 역행 검사도 경로가 바뀌면 건너뛰어집니다.
- **수정 방안:**
  - `initialize`에서 DB 안에 무작위 `installation_id`(메타 테이블)를 만들고, `source_id = HMAC(subkey, installation_id)`로 바꿉니다.
  - 스냅샷에 이 ID가 없으면 백업을 거부합니다.
  - 기존 경로 기반 체인에서 옮겨 올 때는 명시적인 재기준(re-anchor) 명령과 감사 기록을 요구합니다.

### N2 — [Low] lane 분리 후 인증 실패 throttle이 토큰 추측 속도를 제한하지 못함

- **코드:** 자격 증명 평가가 rate limit보다 먼저 실행됩니다(`api.py:289-302`). 맞는 토큰은 `issuer`/`admin` lane, 틀린 토큰은 `*_auth` lane으로 갑니다(`310-321`).
- **동작:** 한 출처의 `*_auth` 쿼터가 소진된 뒤에는 틀린 추측은 429, 맞는 추측은 2xx를 받습니다. 결국 추측 횟수가 처리량으로만 제한되고, 성공 여부도 구분됩니다.
- **추가 비용:** 잘못된 issuer 요청마다 rate limit 전에 SQLite 읽기 트랜잭션이 하나씩 실행됩니다(`297-299`).
- **전제 조건:** 추측 가능한 토큰이 있어야 합니다. issuer 토큰은 256비트 무작위이고(`api.py:422`, `470`) 운영 관리자 토큰은 `_production_secret_is_valid`를 거치므로 실질 위험은 낮습니다. 비운영 모드의 관리자 토큰은 길이 32자 이상만 요구합니다(`api.py:218`).
- **수정 방안:**
  - 모든 모드에서 관리자 토큰의 엔트로피를 강제합니다.
  - 출처와 무관한 전역 인증 실패율 경보를 둡니다.
  - 인증 전 단계에 출처별 동시성 상한을 둡니다.
  - lane 분리가 의도된 trade-off라면 문서에 명시합니다.

### N3 — [Low] 인증 없고 throttle 없는 `/health`가 매 요청마다 CRL 번들 전체를 처리함

- **코드:** 운영 모드의 `health()`가 매번 `tls_configuration_status()`를 호출합니다(`api.py:407-408`). 이 함수는 최대 4 MiB 파일을 두 번 읽고, 정규식으로 스캔하고, CRL을 모두 파싱하고, OpenSSL `load_verify_locations`까지 실행합니다(`analyzer.py:77-102`).
- `/health`는 보호 경로 목록(`api.py:267`)에 없어서 rate limit을 받지 않습니다. 동기 엔드포인트라 공용 스레드풀 슬롯을 차지합니다.
- **전제 조건:** 외부에서 `/health`에 접근할 수 있고, CRL 번들이 큰 경우입니다.
- **영향:** 요청을 대량으로 보내면 CPU와 I/O가 증폭되고, 스레드풀이 고갈되어 다른 API, 특히 rate-limit 처리가 지연될 수 있습니다.
- **수정 방안:**
  - `(st_mtime_ns, st_size, st_ino)`를 키로 상태를 캐시하거나, maintenance 루프에서 주기적으로 계산합니다.
  - health는 캐시된 값만 반환하고, 필요하면 rate limit을 적용합니다.
  - 요청 시점의 엄격한 컨텍스트 생성은 지금처럼 유지합니다.

### N4 — [Info] 백업 세대 순서와 감사 검사의 경계 사례

- **스냅샷 시점:** 스냅샷은 체크포인트 락 밖에서 찍힙니다(`secure_profile.py:281-290`, 락은 `313`). 동시에 두 백업이 돌면 더 오래된 스냅샷이 더 높은 세대를 받을 수 있습니다. 감사 최대 ID가 같을 때만 통과하므로, 차이는 감사 기록이 남지 않는 테이블(보안 이벤트, 카운터)에 한정됩니다.
- **감사 테이블 부재:** 현재 스냅샷에 `audit_events`가 없으면 `audit_max is None`이 되어 역행 검사를 건너뜁니다(`315`).
- **롤백 승인 후 백업 실패:** 롤백 복원을 승인한 뒤 같은 경로로 백업하면, 감사 ID가 이전 최대치를 넘을 때까지 백업이 실패합니다. 공식적인 재기준 수단이 없어서 운영자가 경로를 바꾸게 되고, 그러면 N1로 이어집니다.
- **외부 백업 ID 처리 불일치:** 체크포인트 파일은 있지만 해당 `source_id` 행이 없을 때는 `expected_backup_id`가 있어도 거부됩니다(`389`). 설계 설명("체크포인트가 없으면 외부 ID 허용")과 다르지만, 안전한 쪽으로 실패합니다.
- **수정 방안:** 스냅샷을 체크포인트 락 안에서 찍습니다. 이전 체크포인트에 감사 최대치가 있는데 현재 스냅샷에 감사 테이블이 없으면 거부합니다. 명시적인 re-anchor 명령을 추가합니다.

(참고, hardening 수준: `backup-key.bin` 하나를 AES-GCM, `source_id` HMAC, 체크포인트 HMAC에 같이 씁니다. 도메인 문자열로 구분되어 있어 구체적인 공격은 확인되지 않았지만, HKDF로 하위 키를 분리하는 편이 좋습니다.)

- **M1:**

  - CHECK가 없거나 예상 밖 그룹 값을 가진 예전 스키마에서 시작이 fail-closed되는지

- **L2:**
  - 같은 DB를 두 경로(또는 Docker staging 두 번)로 백업한 뒤 오래된 쪽 복원이 거부되는지(N1, 현재 코드에서는 실패할 것으로 예상)
  - 체크포인트는 있으나 행이 없을 때 `expected_backup_id` 처리
  - 잘못된 메타데이터 타입(`generation=True`, `created_at` 누락이나 비UTC, 메타데이터가 리스트인 경우)
  - 동시 백업 시 세대 순서
  - 실제 Docker 흐름에서 롤백 거부 경로 (현재 `check_encrypted_docker_backup.py`는 최신 백업 복원만 확인합니다)
- **L4:**
  - 만료된 블록과 유효한 블록이 섞인 번들
  - `create_app` 수준에서 `crl_not_yet_valid` 상태로 시작
  - `/health` 반복 호출 비용이나 캐시(N3)

## 남은 발견 사항

### R1 — Low (N1 잔여): 식별자 테이블이 없으면 경고 없이 새 신뢰 체인이 시작됨
- **코드:** `storage.py:219-224`, `:248-256`; `secure_profile.py:301`, `:336` (이전 체크포인트가 없으면 1세대)
- **동작:**
  - `initialize()`는 `backup_identity` *테이블이 없으면* 데이터가 있는 DB여도 새 식별자를 만듭니다.
  - 업그레이드 이전 DB 사본이나 테이블이 삭제된 사본으로 앱을 시작한 뒤 운영 프로필로 백업하면, 이전 상태(이후 폐기가 빠진 상태)가 새 source_id의 1세대가 됩니다.
  - 이 백업은 해당 체인의 "최신"이므로 `--allow-rollback` 없이 기본 복원이 허용됩니다.
- **전제 조건:** 운영자가 그 사본에서 initialize와 백업을 실행해야 합니다. 백업 저장소만 통제하는 공격자는 악용할 수 없습니다.
- **문서 불일치:** `RECOVERY_CHECK.md:15`는 "존재하던 식별자가 없거나 손상되면 자동 교체하지 않는다"고 하지만, 테이블이 없는 경우에는 자동으로 생성됩니다.
- **권장:**
  - 체크포인트 저장소에 기록된 적 없는 source_id의 첫 백업에는 `--new-installation` 같은 명시적 승인을 요구하고, 결과에 기록합니다.
  - 데이터가 있는 DB를 처음 마이그레이션할 때는 별도 명령을 쓰게 합니다.
  - 최소한 문서를 실제 동작에 맞게 고칩니다.

### 정보성 (결함이 아닌 운영·견고성 주의점)
- **I1 — 갈라진 복제본을 구분하지 못함:** 같은 식별자를 가진 복제본이 따로 변경되어도 `audit MAX(id)`가 이전 값 이상이면 같은 체인의 다음 세대로 받아들여집니다 (`secure_profile.py:316`). 계보(lineage)를 증명하지 않는다는 뜻입니다. 운영 프로필로 스테이징 복제본을 백업하지 않는 운영 조건이 필요하며, 감사 로그 앞부분의 해시를 체크포인트에 저장하면 보강할 수 있습니다.
- **I2 — 복원 실패 시 산출물이 남음:** 재고정 경로가 `write_restored_state()`를 체크포인트 INSERT보다 먼저 실행합니다 (`:421-431`).
  - 파일이 없을 때의 분기(`:427-431`)는 잠금 안에서 latest를 다시 읽지 않습니다. 그래서 그 사이 동시 백업이 끼어들면 IntegrityError로 실패하지만, 복원 파일은 private 디렉터리에 남습니다.
  - 체크포인트 자체는 fail-closed라서 롤백이 승인되지는 않습니다.
  - 첫 백업이 실패하면 테이블 없는 빈 체크포인트 파일이 남을 수 있습니다 (`:233-242`). 이 경우 이후 외부 ID로 재고정하는 대신 SQLite 오류가 나며, 가용성에만 영향이 있습니다.
- **N2 관련:**
  - 슬롯은 *프로세스별·역할 전체 공용*입니다. 인증되지 않은 동시 요청 폭주만으로 정상 기관 사용자도 `429 busy`를 받을 수 있습니다.
  - 속도 제한 확인이 인증 평가 *뒤에* 있으므로, 이미 제한된 출처도 슬롯을 차지하고 토큰 평가를 일으킵니다.
  - `OPERATION_SECURITY.md:30`이 이를 대체로 설명하지만, "정상 사용자도 같은 슬롯을 공유한다"는 점을 명시하기를 권장합니다.
  - 관리자 확인은 이벤트 루프 안의 동기 코드라서 관리자 슬롯은 실제로 경합되지 않습니다. 결함은 아닙니다.
  - 이 슬롯은 추측 토큰 잠금(lockout)이 아니며, 분당 평가 횟수의 상한도 아닙니다.

## 빠진 핵심 테스트
1. 데이터가 있는 DB에서 `backup_identity`를 삭제하거나 업그레이드 이전 DB로 `initialize`를 실행했을 때의 동작, 그리고 그 결과 1세대 백업이 기본 복원되는지 (R1)
2. 경로 기반 구형 v2(`identity_format` 없음)의 기본 거부와 `allow_rollback`으로만 허용되는지. 현재는 v1만 테스트됩니다.
3. 메타데이터의 `installation_id`/`source_id`가 복원된 DB와 맞지 않을 때 거부하는지 (`:393-394` 경로)
4. 같은 설치를 동시에 백업할 때 세대가 서로 다르고 순서대로 매겨지는지 (스레드/프로세스)
