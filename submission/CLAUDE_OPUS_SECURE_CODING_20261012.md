## 확인된 문제

### F-1. 공개 요청 한도가 모든 사용자의 공통 한도로 합쳐짐 — 높음

운영 경로는 Nginx → 호스트의 `127.0.0.1:8002` → Docker 앱이다. Nginx가 `X-Forwarded-For`와 `X-Real-IP`를 지우고, Uvicorn은 `proxy_headers=False`로 실행된다. 앱은 `request.client.host`를 요청 한도 키에 넣는다. 따라서 추적된 배포 설정대로라면 시민별 주소가 아닌 프록시의 동일한 주소로 `/verify` 분당 60회, `/analyze` 분당 10회 한도를 공유한다. 인증된 기관 요청도 분당 30회 공통 한도다. 한도는 본문 처리 전에 소진되므로 한 클라이언트가 정상 사용자의 검증·분석을 429로 막을 수 있다. Nginx의 IP별 초당 30회 한도는 이보다 느린 요청을 막지 못한다.

근거: `deploy/nginx-onjeon.conf:2,23,36-42`, `compose.production.yaml:7-8`, `scripts/run_production_server.py:16-17`, `src/onjeon/api.py:313,320-329`, `src/onjeon/storage.py:121-122`. `tests/test_api.py:465-469`는 위조된 전달 헤더를 무시하는 동작을 확인하지만, 운영 프록시 뒤에서 사용자별 한도가 분리되는지는 검증하지 않는다.

**조치 방향:** Nginx가 기존 전달 헤더를 덮어써 실제 접속 주소를 전달하고, 앱은 검증된 프록시 피어에서 온 헤더만 신뢰하게 한다. 기관 요청은 인증된 기관 식별자별 한도로 분리한다. 프록시 헤더 위조 차단, 서로 다른 시민의 한도 분리, 기관 간 한도 분리를 회귀 테스트와 배포 설정 검사로 확인해야 한다. 실제 서버 설정을 이번 점검에서 다시 읽지는 않았으므로 운영 적용 여부는 배포 전에 재확인해야 한다.

### F-2. 인증 실패 감사 기록의 SQLite 쓰기 경합 가능성 — 낮음, 영향 미측정

`/admin/*`, `/institutions/*`의 401·403·429 응답은 감사 기록을 남긴다. 기록마다 SQLite 쓰기 트랜잭션을 열고 오래된 기록 삭제 및 최대 1만 행 정리를 수행한다. 요청 한도 검사도 별도의 쓰기 트랜잭션을 사용한다. 여러 출처에서 실패 요청이 몰리면 DB 잠금 경합으로 정상 `/verify`의 한도 검사까지 실패할 가능성이 있다. 코드 경로는 확인했지만 부하 시험은 하지 않아 처리량이나 장애 임계값은 알 수 없다.

근거: `src/onjeon/api.py:325-327,354-400`, `src/onjeon/storage.py:123-178`. 정리 작업을 요청 경로 밖으로 옮기거나 감사 이벤트를 집계하는 방안을 검토할 수 있다. 이때 보존 기간과 최대 기록 수를 유지해야 한다.
