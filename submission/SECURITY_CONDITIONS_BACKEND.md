검토일: 2026-10-11 KST. 아래 실증은 임시 SQLite·임시 발급키·무작위 시험 토큰만 사용했다. 기존 실제 DB·개인키·기관 토큰을 조사하거나 변경하지 않았다. Docker·TLS 실증은 통합 보고서를 따른다.

## S14: 생산 구형 토큰 거부

`ONJEON_ENV=production`에서는 `sha256$<64hex 솔트>$<64hex 해시>`만 기관 인증에 허용한다. 무솔트64hex와16바이트 솔트 형식은403으로 거부한다. 개발 모드는 기존 호환을 유지한다. 이 정책이 기존 DB 토큰 해시를 자동으로 변경하지 않는지 실제 API 시험으로 확인했다.

안전한 전환은 운영자가 승인한 유지보수 시간에 수행한다. 별도 암호화 백업·관리자 자격증명·생산 CRL 구성을 준비하고 관리자 API로 해당 기관 토큰을 명시적으로 회전한다. 새 토큰은 안전한 채널로 담당자에게 한 번 전달한다. 신규 토큰의 기관 대시보드 접근과 이전 토큰403을 확인한 뒤 서비스를 재개한다. 기관 담당자가 브라우저에서 나가는 행동은 서버 토큰의 폐기를 뜻하지 않는다. 승인 없는 실제 토큰 교체나 구형 해시의 가짜 업그레이드는 하지 않는다.

근거 시험: `test_production_rejects_legacy_issuer_hash_without_replacing_credentials`의 무솔트·16바이트솔트2가지 경우. 각각 개발200, 생산403, DB 기존값 불변, 관리자 명시 회전201/200, 이전 토큰403을 검증했다.

## S16: 공유·영속 요청 제한

모든 환경의 보호 API는 같은 SQLite DB의 `rate_counters`를 사용한다. 프로세스 내 쓰기 잠금과 SQLite `BEGIN IMMEDIATE`가 검사·증가를 한 트랜잭션으로 수행한다. 프로세스가 늘거나 재시작해도 카운터를 초기화하지 않는다.

| 요청 그룹 | 같은 peer의 한 UTC분 한도 |
|---|---:|
| `/verify` | 60 |
| `/analyze` | 10 |
| `/institutions/…` 인증 성공 (`issuer`) | 30 |
| `/admin/…` 인증 성공 (`admin`) | 30 |
| `/institutions/…` 인증 실패 (`issuer_auth`) | 30 |
| `/admin/…` 인증 실패 (`admin_auth`) | 30 |

분 창은 UTC 시계의 고정60초 구간이다. 따라서 경계 직전·직후의 요청이 각각 다음 창에 포함될 수 있다. 임의의 연속60초에 항상 같은 총량을 보장하는 이동 창이라고 설명하지 않는다. 시스템 시계와 영속 볼륨은 운영자가 보호해야 한다.

본문을 읽기 전에 제한한다. DB 접근 실패·1초 잠금 대기 초과·카운터 수용량 초과도429로 거부하며 공통 보안헤더를 유지한다. 고정 6개 그룹의 행 상한과 횟수를 따로 집행하므로 검증·분석 수용량이나 실패한 인증 요청이 정상 관리·기관 한도를 소진하지 않는다. 정상 카운터를 쫓아내 제한을 우회시키지 않는다. 직접 peer만 사용하고 `X-Forwarded-For`를 앱에서 신뢰하지 않는다. 같은 프록시/NAT peer의 정상 사용자들은 여전히 정상 그룹 한도를 공유한다. Uvicorn의 프록시 헤더 해석도 꺼 두어야 하며 Docker CMD와 시연 서버는 `--no-proxy-headers`/`proxy_headers=False`를 적용한다.

### 카운터의 최소 저장과 권한

DB에는 요청 그룹·분마다 달라지는 HMAC-SHA256 식별자·분 시작 시각·횟수만 저장한다. 원문 IP·헤더·URL·QR·사용자 또는 토큰 내용은 저장하지 않는다. IPv6는/64로 묶는다. 이 자료는 단기 서비스 제한 집계이며 시민의 스캔 내용을 기록하는 검증 이력이 아니다.

HMAC키는 DB 부모의 `.rate-limit-hmac`에32바이트 OS CSPRNG로 만들고 DB와 분리한다. POSIX0600이며 새 DB 디렉터리는0700이다. 완성된 임시 파일을 원자적으로 연결해 여러 프로세스의 첫 실행 경합을 처리하고, 기존 키를 덮어쓰지 않는다. 손상된 키는 자동 교체하지 않고 시작을 거부한다. NTFS에서는 운영 ACL 검증이 필요하다.

카운터는 `admin`, `issuer`, `verify`, `analyze`, `admin_auth`, `issuer_auth` 고정 6개 그룹별 최대10,000행이다. 현재 UTC분의 행만 보존하며 지난 분의 행은 시작·사용·정리 작업에서 삭제한다. 이 그룹별 상한은 실패 감사의 전체10,000행 상한과 별개다. 키·DB를 함께 영속 보관해야 한다. HMAC키의 삭제·교체 또는 오래된 DB 복구는 기존 창 제한을 잃을 수 있으므로 승인된 복구 절차 밖에서는 허용하지 않는다. 백업에는 별도 암호화·권한 보호와 HMAC키 동시 복원이 필요하다. 해당 복구를 `check_recovery.py`로 실제 확인했다.

### 실제 프로세스 실증

`test_two_real_processes_and_restart_share_atomic_rate_limit`를 Windows/Python3.12.10에서 실제 spawn 프로세스로 실행했다. 같은 임시 DB·동일 합성 peer·같은 분 창으로 두 프로세스가 각각40회 실제 `/verify` API를 호출했다.

```json
{"two_process_ids":[33544,50308],"requests":80,"accepted":60,"limited":20,"restart_process_id":21672,"restart_limited":1}
```

두 프로세스의 합계60회만200, 나머지20회는429였다. 두 프로세스를 종료하고 새 프로세스를 시작해도 추가 요청은429였다. DB에는 해당 창의 한 행·횟수60만 남았고 원문 peer 문자열은 없었다.

추가 시험은 그룹별 카운터 상한 도달 시 기존 창 유지·새 peer 거부, 현재 분 경계의 지난 창 정리·HMAC 식별자 변경, 실패 인증과 정상 요청의 별도 한도,60개의 서로 다른 위조 XFF에도 peer 한도 유지, DB 장애429와 원문 예외 비노출을 검사한다. 위 실제 프로세스 JSON과 아래 실행 숫자는 해당 시점의 기록을 보존했으며 현행 변경 후 실행 결과는 최신 `TEST_REPORT.md`를 따른다.

### 동시 시작 경합 수정

최종 회귀에서 발견한 시작 실패를 실제 프로세스의 Barrier로 재현했다. 수정 전 새 DB 동시 시작3회 중2회가 `startup/OperationalError/SQLITE_BUSY(5)`로 실패했다. 오류 관찰 자료에는 단계·예외 클래스·SQLite 숫자 코드만 담고 원문 예외나 경로·비밀값은 담지 않았다. 합성 시계는 같은 분으로 고정해 분 경계의 영향을 배제했다.

초기화는 WAL 전환과 `BEGIN IMMEDIATE`에 한해 BUSY/LOCKED를 최대5초 동안 재시도한다. 다른 오류는 즉시 실패한다. 고정 스키마 생성·기존 컬럼 검사와 추가·인덱스 생성·보존 정리는 하나의 쓰기 트랜잭션에서 수행한다. `executescript()`의 암묵적 커밋을 제거해 다른 프로세스가 마이그레이션 중간 상태를 읽고 동일 컬럼을 추가하는 경합도 막았다. 제한 시간 뒤에도 잠금이 풀리지 않으면 서버 시작을 거부한다.

수정 후 새 DB와 구형 DB를 각각2회 동시 시작하고, 매회 두 프로세스의80회 요청과 별도 재시작 요청을 확인했다. 네 경우 모두60회200·20회429였으며 재시작 후 추가 요청은429였다. 구형 기관 자료는 유지되고 컬럼 마이그레이션도 완료됐다. HMAC키는 완성된 파일을 한 번 연결하는 기존 절차를 유지했다.

```json
{"fresh":[{"processes":[15216,33880],"restart":50780},{"processes":[44924,29676],"restart":51416}],"legacy":[{"processes":[32128,30452],"restart":50692},{"processes":[36060,26760],"restart":43852}],"each_run":{"requests":80,"accepted":60,"limited":20,"restart_limited":1}}
```

## 유휴 보존 정리

ASGI lifespan은 정리 작업을 하나 시작해60초마다 `maintenance()`를 스레드 풀에서 실행한다. 요청이 없어도 실패 감사의7일 TTL·전체 최대10,000행과 요청 카운터의 지난 분 행을 정리한다. 카운터는 현재 분·그룹별 최대10,000행을 유지한다. 종료 시 정리 task를 취소하고 기다린다. 정리 실패는 고정 `SECURITY_MAINTENANCE_FAILED`만 운영 로그에 남긴다. 중단된 서버는 작업을 실행할 수 없으므로 다음 시작 때도 정리한다. 저장장치의 안전 소거나 이미 만들어진 별도 백업 삭제까지 보장하지 않는다.

`test_idle_lifespan_maintenance_removes_expired_rows`에서는 제어된 짧은 주기로 HTTP 요청 없이 만료 자료가 사라짐을 확인했다. 기본60초 주기도 별도 임시 환경에서61.011초 실행했다. HTTP 요청0회 상태에서 만료 감사·카운터가 모두 사라졌고 종료 후 임시 파일도 제거했다.

```json
{"default_interval_seconds":60,"elapsed_seconds":61.011,"http_requests":0,"expired_security_rows_remaining":0,"expired_rate_rows_remaining":0,"temporary_state_removed":true}
```

## S09·S11 생산 시작 조건

관리자 토큰·키 암호는 최소32자, 최소8종 문자,16자 이하 반복 패턴·demo/test/changeme/default/password 예시 패턴 거부를 적용한다. 이 검사는 눈에 띄는 취약 설정을 막는 보조 장치이며 문자열만으로 엔트로피를 증명하지 않는다. 생산용 값은 배포 프로필의 CSPRNG 생성 절차로 준비한다. 비밀값을 예외·로그·보고서에 출력하지 않는다.

생산 시작은 `analyzer.tls_configuration_status()`로 로컬 CRL-only PEM 구성을 검증한다. 정상 형식·시간 구간의 CRL이 현재 만료되었거나 아직 발효하지 않았다면 URL 분석만 차단하고 `/health`에 `degraded`·`url_analysis` 사유를 표시한다. QR 검증·발급·관리 기능은 유지하며 정상 CRL로 갱신하면 다음 조회·분석부터 회복한다. CRL 설정 누락·손상·CA 혼입·잘못된 시간 구간·운영 `SSLKEYLOGFILE`은 시작 실패다. URL 연결은 `build_tls_context()`의 엄격한 검증을 유지하며 체인·CRL 서명·해지·호스트 검사와 실증은 TLS 보고서를 따른다. 아래 기존 API·시연 기록은 당시 현재 유효 CRL을 사용한 실행 증거로 보존한다. `run_security_demo.py`도 임시 CRL을 생성한다. 복구 실증은 외부망을 쓰지 않는 명시적 개발 모드다.
