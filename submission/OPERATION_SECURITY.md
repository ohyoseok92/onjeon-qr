## TLS와 인증서 해지

URL 분석기는 인증서 CA 체인·호스트명·유효기간을 검사한다. 실제 로컬 TLS 회귀에는 자체 서명·호스트명 불일치·내부망 이동·시간 제한이 포함된다. production은 CRL-only PEM 필수·VERIFY_CRL_CHECK_CHAIN을 적용한다. 실제 TLS 정상·폐기·CRL서명 변조·만료·누락·교체 후 차단을 확인했다. 정상 형식·시간 구간의 CRL이 현재 만료 또는 미래 발효 상태이면 URL 분석을 차단하고 `/health`의 `status=degraded`, `url_analysis.available=false`와 고정 사유를 표시한다. QR 검증·발급·관리 기능은 유지하며 정상 CRL 갱신 후 회복한다. CRL 설정 누락·손상·CA 인증서 혼입·잘못된 시간 구간·운영 `SSLKEYLOGFILE`은 시작을 거부한다. HTTP 200만으로 URL 분석 준비 완료를 판정하지 않고 상태 본문을 확인해야 한다. S11의 남은 조건은 운영 CRL 확보/갱신/antirollback·대상 발급자 범위다. 로컬 시험 CA를 OS에 설치하지 않았고 공개 배포나 전체 WebPKI 지원으로 주장하지 않는다.

운영 키는 `<기관ID>/<키버전>.pem` 중첩 경로만 사용한다. 구분자 충돌이 가능한 `<기관ID>-<키버전>.pem` 레거시 경로는 로컬 데모에서만 허용하며, 운영에서 중첩 키가 없으면 발급은 503, 키 활성화·교체는 422로 거부한다.

## 로그·보존·복구 조건

기관/관리자 인증 실패와 429 이벤트는 고정 사건명·응답코드·등록기관·시각·분 단위 횟수·일/프로세스별 HMAC 식별만 저장한다. 시민 verify/analyze 원문·주소·토큰·원시 IP는 저장하지 않는다. 감사는 7일·전체 10,000행 범위로 보존한다. 요청 제한은 SQLite의 `admin`, `issuer`, `verify`, `analyze`, `admin_auth`, `issuer_auth` 고정 6개 그룹을 사용하며 각 그룹 최대 10,000행이다. 지난 분의 카운터는 시작·사용 및 lifespan 60초 주기로 삭제한다. 잘못된 인증은 별도 auth 그룹의 30회/분 한도를 쓰며 정상 관리·기관 요청의 몫을 소진하지 않는다. 정상 요청의 관리·기관 각 30회, 검증 60회, 분석 10회 한도는 출처별 고정 분 단위로 적용한다. HTTP 0회·61초의 기본 정리 주기 시험과 다중 프로세스·재시작 제한 유지 증거는 최신 시험 보고서를 따른다. 감사 DB 장애는 인증 실패 응답을 유지하고 고정 오류 코드만 제한적으로 기록한다.

같은 로컬 SQLite를 공유하면 워커와 재시작에 걸쳐 제한을 유지한다. DB가 다른 여러 호스트의 중앙 집행은 별도 운영 조건이다. 수정된 공개 운영 구성을 배포하면 Nginx가 실제 접속 IP로 전달 헤더를 덮어쓰고 Uvicorn은 전용 Docker 브리지 게이트웨이 한 주소만 신뢰한다. 시민 한도는 전달된 IP별, 인증된 기관 한도는 기관 ID별이다. 같은 NAT 공인 IP를 쓰는 시민은 한도를 공유한다. 개발·시연 서버는 전달 헤더를 무시한다.

정상·실패 그룹을 구분하려면 인증을 먼저 평가해야 한다. 실패 한도 뒤의 잘못된 토큰429·정상 토큰200 동작은 정상 사용자의 몫을 보호하는 정책이며 토큰 비교 자체를 분당30회로 막는 통제는 아니다. 기관 분류에는 DB 읽기 비용도 든다. 이를 위해 앱 인스턴스마다 관리자·기관 역할별 독립 슬롯8개를 두고, 포화된 역할은 다음 토큰 평가·기관 DB 조회 전에 `429 / Authentication checks busy`로 거부한다. 정상 완료와 예외 경로에서 슬롯을 반환한다. 이 동시성 상한은 지속 요청률이나 여러 워커 전체의 총량을 제한하지 않으므로 고엔트로피 운영 토큰과 프록시·연결·중앙 제한 정책을 함께 유지해야 한다.

브라우저 상태 제거는 이후 앱 사용으로 토큰을 다시 노출하지 않기 위한 통제다. JavaScript 메모리의 물리적 영점화나 운영체제 crash dump의 제거를 보장하지 않는다. 프록시/관측 도구의 별도 접근 로그와 백업에는 운영 접근권한·보존기한을 적용해야 한다.

암호화 백업의 v2 생성 시각·세대·감사 ID·DB 해시는 함께 인증하며, 백업 저장소 밖의 HMAC 체크포인트와 대조해 이전 세대 복원을 기본 거부한다. key-custody와 최신 백업 ID를 별도 신뢰 매체에서 보관해야 한다. 체크포인트를 잃으면 독립 채널의 기대 백업 ID가 필요하며, 이전 복구 예외는 `--allow-rollback`으로 명시한다. 최신 백업에도 이후 보안 변경은 들어 있지 않으므로 생성 시각·감사 ID 이후의 폐기·기관 비활성·토큰 교체를 재적용하고 승인한 뒤 서비스를 재개한다. `RECOVERY_CHECK.md`에 복원 거부와 예외 절차를 구분했다.

health의 CRL 상태는 앱별 잠금으로 최대5초 캐시한다. 반복 health 요청이 매번 CRL 전체를 파싱하지 않으며 갱신 상태 표시에 최대5초 지연이 있다. 실제 URL 분석의 TLS 검사는 캐시를 사용하지 않고 매 요청 엄격하게 수행한다. 백업의 논리적 설치 ID는 DB에 저장되어 임시 경로가 바뀌어도 같은 세대를 사용한다. 원본 ID 또는 감사 체크포인트가 없으면 새 백업을 거부한다.

새 설치의 첫 백업은 운영자가 신뢰 기준을 확인하고 `--new-installation`을 명시해야 한다. 구형 DB에서 새 ID가 생성되어도 체크포인트에 조용히 등록되지 않는다. 인증 분류 슬롯은 역할별로 정상·실패 요청이 함께 쓰므로 동시 실패 요청이 정상 기관 요청에도 busy429를 만들 수 있다. 높은 엔트로피 토큰·앞단 부하 통제와 경보가 필요하며, 분당 토큰 평가 제한으로 주장하지 않는다.
